# WOK步战阵营与编制文档编写规则

规范版本：1.0　修订日期：2026-09-06

配套离线编辑器源码位于 `tools/loadout-editor/`，使用方式见该目录 `README.md`。除本文的表格文档外，工作人员也可提交编辑器生成的 `wok_infantry_editor_project` 工程文件；它保留完整修改基线和当前目录，适合继续编辑及三方合并。游戏导入使用另行导出的 `wok_infantry_catalog` 数据包，不能把工程文件或局部配装表直接当完整目录导入。旧文档导入约定仍适用于范围核对、资源映射和冲突处理。

这份规则供编制策划、配装设计和数据整理人员共同使用。按规则交付后，将文件交给导入负责人或 Codex，即可核对资源、生成配置差异，并按指定范围导入。作者不必编写 Java 或手工拼接 JSON。

版式参考《步战模式公示表.xlsx》的“阵营”工作表：横向对照不同编制，纵向保留名称、种类、简介、特色、优缺点及各类力量。公示表负责讲清设计，附表负责给出可执行数据。本文规定的是**文档交付与辅助导入约定**；当前游戏没有直接读取 Word、Excel 或本规范文档的按钮。

## 1 交付方式

优先填写随附《WOK步战阵营编制填写模板.xlsx》。也可提交 Word 或 Markdown，沿用本规则的标题和表头。必须保留可复制文字；图片、截图和 PDF 扫描件不能作为唯一数据来源。

每个文档写明作者、文档编号、修订号、日期、导入范围，以及基于哪份已有配置修改。文档修订号与 MOD 版本号无关，写文档不得顺带提升 MOD 版本。

- **新增**：添加一个新对象，保留现有阵营、其他编制与配装。
- **修改**：使用现有稳定 ID，仅修改本次明确列出的内容。
- **删除**：在修改清单中逐项写出稳定 ID。删掉表中一行不表示删除游戏对象。
- **替换完整编制**：明确写“替换完整编制”，列出需要保留和删除的职业、载具与能力；不能以“更新”两字代替。

本次只想改简介、载具或支援时，导入范围只写相应项。未列入范围的项目保持原样。后续交回模板时，删除未使用的整列编制草稿；明细表的空白预留行不作为记录。明细行不够时复制同类填写行并保留表头与校验；不要在表格外另散写要导入的数据。

## 2 阵营和组织层级

必须分别填写以下概念，不能用一个“阵营名”包办：

| 层级 | 含义 | 现有示例 |
| --- | --- | --- |
| 内部战斗侧 | 游戏用于交战与胜负判定的蓝／红侧 | `blue`、`red` |
| 公开阵营 | 玩家在当前战局选择的阵营 | 学院军 `academy`、凯撒 `caesar` |
| 所属组织 | 公示表中的学院、军队、公司或分支分组 | 格赫娜学院军 GDF、圣三一卫队 TRG、千禧年联合作战部队 MJF |
| 具体编制 | 可供该公开阵营选用的一套作战编制 | 研讨会机动部队、研讨会骑兵军团 |

**当前框架最多同时启用两个公开阵营，blue 和 red 各一个。**原公示表中的三个学院军组织不能直接追加成三个独立蓝方公开阵营。组织名称目前作为文档分组或简介保存，不会自动生成新的 UI 选择层。新增第三个可交战阵营或新增组织选择层，需要另做框架功能。

名称可以中文，稳定 ID 用于定位同一个对象。修改名称不应修改 ID。例如“第234机械化作战单元”与已有的“234机械化作战单元”应先核对是否都是 `caesar_234_mechanized`，不得仅凭显示名称再建一份。

## 3 公示表的固定栏目

公示表每一列只写一个具体编制。可以合并展示组织标题，但导入附表的每条记录必须写出归属，不能依赖合并单元格、颜色或“同上”。

| 栏目 | 写作要求 |
| --- | --- |
| 所属组织／分支 | 写完整组织名；共享背景单独写，避免将一段组织简介误当成所有编制的具体能力 |
| 名称 | 一个正式名称；别名放在备注，不用斜杠堆多个正式名称 |
| 种类 | 保留“进攻型装甲旅”等中文设定，并在附表单独选游戏类别 |
| 简介 | 说明隶属、主要装备、作战方式；导入游戏的简介不超过 512 个字符，长背景另附 |
| 军种特色 | 一句话描述主要特点，不在这里埋藏未登记的倍率和技能 |
| 核心优点 | 每行一个可理解的优势；涉及加成时必须在明细中给出数值和范围 |
| 核心缺点 | 每行一个限制；“无机枪”“无 FOB”“不可再生”等必须与明细一致 |
| 装甲力量 | 每行一种明确型号，写数量、是否补充、最终补充时间，空军运输载具也列入 |
| 步兵力量 | 写职业、主要武器与护甲、特殊单位；名额、弹药和装备细节落到明细 |
| 支援力量 | 每行一个支援，写可用情况；冷却和效果变更须单独登记 |
| 战场定位 | 说明适用地形、任务与协同方式，不额外创造隐藏属性 |

原表的种类色块、绿色优点行与红色缺点行可以保留，但颜色不代表可执行数据。用文字写清“允许”“禁用”“继承”，不能只靠背景色区分。

## 4 数字和空值写法

1. 人数、车辆数、物品数、弹药发数用整数。时间明细统一为秒，距离统一为游戏格，角度用度。公示文案可以展示分钟。
2. 不省略数量。`小鸟 机枪版（10分钟）`应写为`小鸟 机枪版 ×1；战损后 600 秒补充`。
3. 不提交算式作为最终值。`15−3分钟`应写为`基准900秒；调整−180秒；最终720秒`，实际填写补充秒数为 `720`。
4. “每小队 2 人”和“全阵营 2 人”必须区分。当前兵种配额主要按小队生效，不能把全阵营配额直接当成每队配额。
5. `无`表示明确没有；`继承`必须写来源及修订号；`保持现状`只用于修改已有对象；`待定`表示设计尚未完成。空白不代表 0、无、删除或继承。
6. 必填项出现空白、待定、待映射、互相矛盾时，先补齐或核对，不自动启用该编制。只影响外观的未定徽标可明确填“无徽标”。
7. Excel 数值列填写真实数字，不写带单位的字符串或公式；表头写单位。备注不得覆盖结构化字段。

## 5 导入登记

每个编制在“导入登记”中填写以下信息：

| 项目 | 规则 |
| --- | --- |
| 文档编号与修订号 | 同一文档持续修订，例如 `formation-plan-001 / r2`；不能把 r2 当成 MOD 版本 |
| 操作与范围 | 使用第 1 节操作；范围明确到阵营说明、编制、载具、职业配装、支援、能力等 |
| 修改基线 | 修改已有对象时填写配置日期、导出包名或哈希；避免旧文档覆盖较新的游戏内编辑 |
| 公开阵营 ID／名称／战斗侧 | 一一对应。当前已有 `academy/blue`、`caesar/red`；新增公开阵营不得占用已被另一阵营使用的战斗侧 |
| 阵营人数上限 | 1–40。只新增编制时可写“保持现状” |
| 编制 ID／名称 | 现有对象沿用 ID；名称不超过 40 个字符 |
| 类别 | `infantry` 步兵、`armored` 装甲、`motorized` 摩步、`mechanized` 机械化、`special` 特种，只选一个 |
| 编制人数上限 | 1–所属阵营上限；不得超过 40 |
| 小队安排 | 最多 5 队，呼号为 `alpha/bravo/charlie/delta/echo`，每队 1–8 人；总席位须覆盖拟开放的编制人数 |
| 初始启用 | 明确“启用”或“停用”，导入前仍须通过必要校验 |
| 徽标 | 已存在的纹理资源 ID，或随附的图片文件，或“无徽标”；外部图片需处理成游戏资源后才会显示 |
| 职业配装、支援、部署能力 | 逐项选择“按明细”“继承指定对象”“保持现状”。支援和载具可明确“无”；启用编制必须有有效职业和小队 |

一个公开阵营当前最多登记 32 个编制；每个编制最多 64 个职业规则、64 个展开后的载具槽位。“进攻型”“防御型”“精锐”“旅／营”等都是中文设定，不会自动变成额外游戏类别、伤害倍率或人数规模。类别为 `armored` 也不会自动增加坦克。

作者不清楚技术 ID 时，可以先写精确中文名、所属 MOD／枪包、已知版本及“待映射”，由导入负责人对照实际注册表补齐。**不能凭简称猜 ID；有多个候选时必须消除歧义。**写完中文设定不等于已经具备全部导入数据。

## 6 载具明细

每行一种配置完全相同的载具。同型号但套件、补充规则或用途不同，要分行。

| 项目 | 必填要求 |
| --- | --- |
| 归属 | 公开阵营 ID + 编制 ID |
| 车型与变体 | 写明确型号、武装、装甲／套件；不要只写“悍马”“布莱德利” |
| 实体 ID | 实际存在的 `namespace:path`；实体 ID 不是载具物品／部署器 ID |
| 数量 | 初始可生成数量，至少 1；没有载具时在登记表写“无”，不要填一条数量 0 的假车辆 |
| 战损补充秒数 | `-1`=本战局不可再生；`0`=无额外冷却但仍受部署条件约束；正数=战损后冷却，上限 86400 |
| 槽位身份 | 新增可由导入负责人分配稳定槽位 ID；修改必须引用既有槽位或上次导入清单，不按本次行号重新编号 |
| 生成布置 | 指定相对部署箭头的坐标与朝向，或明确“自动安全排布”；后者由导入负责人按尺寸计算并检查碰撞，不能全填零坐标 |

“数量 3”会展开成三个独立 `vehicles[]` 槽位。三个槽位同车型但 ID 不同；减少数量或改 ID 可能触发旧载具清理，必须列进修改影响。战损补充不是每隔固定时间无限赠送车辆。

当前编制载具接入允许的 namespace 为 `superbwarfare`、`fcp`、`dragonrise_reforge`。公示表里出现的其他来源（例如 `vvp`）不能仅因整合包已安装就视为编制生成已支持；需要先检查或扩展接入层。

样例格式：`M1296 龙骑兵；fcp:stryker_dragoon；数量3；补充秒数-1`。这是一条字段写法示例，不授权改变任一现有编制。

### 运输补给与车辆平衡

运输规格写 `large` 大型或 `medium` 中型，容量写**每辆车首次建立运输数据时的箱数**。没有运输功能写“无”，数量未知写“待定”。规格与数量都要填，不能只写“3箱补给”。

已确认规则：FMTV `superbwarfare:truck` 为大型 3；Ural `fcp:ural` 为大型 3；无装甲无武装 HMMWV `fcp:hmmwv_unarmored_unarmed` 为中型 2；装甲无武装 HMMWV `fcp:hmmwv_armored_unarmed` 为中型 1。

运输按实体类型配置，不是每个编制的一份私有数值。同型号在两个编制里填写不同容量会冲突。调整运输必须同步 `SUPPLY_TRANSPORT_CAPACITY_LIST.md`、服务端默认配置与验收记录；已有车剩余量继续持久化，不能因重启或提高容量而补满。

载具血量、部件上限、T 级和火炮伤害另列“平衡变更”：目标类型／实体、原值、新值、单位、影响范围。当前分类平衡主要在 `wok_vehicle_health` 实现中，写进编制文档不会自动改变它。未进入导入范围的平衡保持现状。

## 7 兵种与配装明细

至少提供一种有效职业。每个职业单独写：名称、稳定职业 ID、显示顺序、每队上限、适用小队和配装来源。指定某小队不允许该职业时，填该队名额 0。不可把“特殊单位 ×2”留成不知是两人、两组还是两辆车。

配装来源三选一：

- **继承副本**：写来源公开阵营、编制、职业 ID 和来源修订号。导入时复制为目标编制的独立装备池，保留来源；之后双方编辑不互相影响。
- **按明细创建**：提供下面全部装备信息。
- **保持现状**：仅用于已有职业的局部修改。

新增职业不得只写武器名单。按明细创建时，每个可选装备条目一行：

| 必填项 | 说明 |
| --- | --- |
| 所属阵营、编制、职业 | 指向登记表与兵种表 |
| 槽位 | 同时写槽位用途和已有 ID（有则沿用），例如主武器、头盔、医疗一；注明是否可选、可空以及发放位置要求 |
| 装备条目与物品 ID | 条目 ID 定位选项；物品 ID 是注册物品；给出完整显示名称 |
| 数量 | 实际发放物品数，不等于备用子弹数 |
| 枪械与配件 | TaCZ 另给 `GunId`、每个配件的 `AttachmentId`；只写 `tacz:modern_kinetic_gun` 无法确定枪型 |
| 弹药上限 | 每把枪条目的 `ammoReserveLimit`，当前 1–4096 发；不要写成整个职业共用上限 |
| 物品状态 | 弹匣状态、弹种、开火模式和其他必要 NBT；优先用管理员终端“读取主手”导出的条目或另附 UTF-8 SNBT 文本 |
| 属性变更 | 明确伤害、穿甲、射速、开镜速度、水平／垂直后坐力、散布的最终倍率；不修改时写“继承来源” |

“主武器 M4A1 或 M16A1”表示两个同槽位可选条目；“M4A1 + 手枪”表示两个同时发放的不同槽位。不能把两种情况都写成逗号列表。仅当白名单对应的条目实际存在时，才允许加入该编制。

倍率采用 `1.00` 为基准。例如“开镜速度降低40%”写最终速度倍率 `0.60`；若修改的是开镜时长，须明确写时长，不能误当速度。穿甲倍率不能当成穿甲率百分点。合法倍率范围由当前编辑器和服务端校验，不能将任意数字都视为已支持。

## 8 支援与部署能力

支援模式选“无”“白名单”或“全部已注册支援”。通常逐项列白名单最明确。每行支援写完整名称、注册 ID、目标、效果说明和本次是否改变数值。仅设置可用支援可映射到 `capabilities.support`。

**冷却、伤害、数量、扫描半径等是支援实现的参数，不是编制白名单字段。**不同编制要求同一个技能采用不同冷却时，先核对是否支持，不得修改共享定义而连带影响所有编制。未注册的新技能、“精锐骑兵光环”“蛙人能力”等作为待开发机制单列，不能以相似技能顶替并声称已导入。

部署能力逐项填写：兵站是否允许、阵营上限、队长／指挥官权限；队包是否允许、每队上限、血量；重生等待秒数；移动重生车辆候选。继承时给出明确来源。

- 当前队包成功部署后的固定小队 CD 为 480 秒；文档不能通过填另一数字宣称已改变该规则。
- 重生等待 `-1` 表示继承，`0–3600` 为具体编制等待秒数。
- 移动重生候选引用的是**编制载具槽位 ID**，不是实体 ID。仅声明候选不等于移动重生的全部运行条件已经接通。
- 兵站策略等字段存在，不代表每个对应交互都已实现。导入报告要分别标注“配置已写入”“运行行为已验证”“待开发”。

## 9 稳定 ID 和配置映射

这一节主要供导入负责人使用。策划可先交完整设计，再由负责人核对技术 ID；发布到游戏前须完成映射。

| 文档信息 | 当前实现位置 |
| --- | --- |
| 公开阵营、编制类别、简介、小队、职业名额、载具槽位、能力策略 | `config/wok_infantry/formations.json`，当前 schema `version=2` |
| 职业装备池、槽位、具体物品、SNBT、逐枪备弹 | `config/wok_infantry/loadouts.json` |
| 运输车辆规格与每车容量 | 核心服务端配置及运输权威清单 |
| 新徽标、新支援技能、未支持的实体来源、载具 T 级数值 | 相应资源或模块代码；视变更构建 JAR，不冒充单纯配置导入 |
| 所属组织、特色、优缺点、战场定位等公示栏目 | 文档保留；需展示到游戏时整理进受长度限制的简介，不能添加游戏忽略的自创 JSON 字段 |

内部稳定 ID 使用 1–64 个小写英文字母、数字、下划线、连字符或点，不含中文、空格与冒号。资源 ID 用 `namespace:path`。同一阵营内编制 ID 唯一；实际导入键为“公开阵营 ID + 编制 ID”。同名不同对象不能合并，同 ID 的显示名变化不能当新增。

新增 ID 可由导入负责人按文档生成并在首次导入清单登记；后续文档必须引用它。重复提交同一修订应得到相同配置结果，不能重新分配职业／装备池 ID 或重复生成载具槽位。

## 10 导入负责人的执行约定

以下是处理此类文档时的工作步骤，不是宣称已经存在一个通用文档解析程序。

1. 读取用户指定的文档与当前配置。参考公示表只提供格式时，不把里面全部设计视为本次启用授权。
2. 按“新增／修改／删除／完整替换”和明确范围生成变更；不以整份新 JSON 覆盖未涉及的已有内容。
3. 核对 MOD、实体、枪械、配件、支援 ID，检查人数、名额、数量、时间、白名单、布置与能力是否可实现。
4. 对比基线与当前实际配置。两者已发生冲突时指出具体字段，未冲突部分可继续整理；不默默回退较新的配装编辑。
5. 导入前生成候选文件、修改清单、未解决项及备份。按用户已授权的范围写入；需要决定的是实质冲突或新增玩法，不为无冲突的常规导入重复索取确认。
6. 关联修改 `formations.json` 与 `loadouts.json` 时成套处理，避免只落地一半；离线替换或使用合适的服务端更新流程。解析失败保留原文件与备份。
7. 需要新增资源或机制时完成相应实现与构建，再说明与配置导入的区别。不得把尚未实现的技能标成“已完成”。
8. 静态检查后在 WOK步战专用环境验证菜单、配装、载具部署、战损补充、权限与重启恢复。未执行的游戏检查明示“未验证”，不能用 JSON 解析通过代替。
9. 返回导入清单：每个对象的稳定 ID、变更前后、生成文件、备份位置、依赖、配置／存档影响、检查结果与待办。保留供下一次修订引用的映射。

当前导入范围不应包含玩家归属、编制投票、世界部署点、占点坐标与载具库存的自动重置。改变载具 ID、删除小队或下调人数可能触发现有状态调和，需要在报告中明确说明。

## 12 作者提交前检查

- 每列编制都能明确找到公开阵营、组织分支、类别和操作范围。
- 公示表与导入明细没有冲突；所有实际改动在修改清单中登记。
- 每种载具有明确数量、变体和补充规则；没有省略数量或未计算的时间表达式。
- 每个职业有明确名额作用域与配装来源；同槽位二选一和同时发放已区分。
- 需要的新技能、独立平衡改动和暂未支持的功能已单列。
- 修改保留既有稳定 ID，提供基线；删除逐项列出，不靠空白表达。
- 必填项无待定；未映射 ID 附有足够定位资料，由导入负责人补齐后再启用。
