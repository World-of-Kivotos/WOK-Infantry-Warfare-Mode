# WOK步战核心：编制大类别与增援机制设计草案

本文记录 `WOK步战核心`（modId：`wok_infantry`）下一阶段的编制大类别设定。本文只整理已经由产品设计明确提出的内容；未给出数值、权限、作用域或流程的部分统一标为“待确认”，不得由实现自行猜测。

## 1. 阵营层级

- 蓝队对应公开阵营“学院军”，稳定 ID 继续使用 `academy`，内部战斗侧为 `blue`。
- 红队对应公开阵营“凯撒军”，稳定 ID 继续使用 `caesar`，内部战斗侧为 `red`。
- 两个阵营下面均存在具体编制。
- 具体编制归入以下大类别：步兵营、装甲营、摩步营、机械化步兵营、特种编制。
- 玩家流程采用三级结构：`阵营 → 编制大类别 → 具体编制`。
- 玩家先选择学院军或凯撒军，再由该阵营的玩家投票选择一个具体编制；胜出编制是阵营共享结果，不是每位玩家各自生效。
- 大类别负责组织具体编制；投票目标是具体编制。学院军与凯撒军的正式具体编制及数量以后分别制定，不预设两边完全对称。

## 2. 大类别设定

### 2.1 步兵营

已明确：

- 核心特色是较强的步兵持续增援能力。
- 步兵营类别下只有“轻步兵营”类具体编制可以部署多个兵站；其他具体编制是否没有兵站或只有一个，由该具体编制配置决定。
- 兵站沿用此前制作的部署信标方块，后续会与配套结构一起放置。
- 其他编制没有兵站或最多只有一个兵站。
- 队长可以部署“队包”。
- 队包与兵站的放置、替换、被毁后恢复和重生相关 CD 都可更短；最终秒数以后按具体编制填写。
- 兵站可由队长或指挥官放置，归属阵营并由同阵营玩家共享。
- 队包采用类似《Squad》的小队集结点规则：是有独立血量、可被摧毁的方块，并且按小队共享。

待确认：

- 轻步兵营的正式名称、数量上限、各项 CD 和队包血量。
- 队包可接受的伤害来源、是否允许友军伤害，以及敌人压制/距离等失效条件。

### 2.2 装甲营

已明确：

- 最多只有一个兵站。
- 拥有多辆坦克支援；普通编制通常只有 1–2 辆坦克，装甲营拥有更多坦克。
- 非装甲车辆数量或种类较少。
- 可用支援技能较少。
- 坦克损毁后的补充时间较长。

待确认：

- 坦克数量、非装甲车辆限制和支援技能限制均不在本阶段写死。

### 2.3 摩步营

已明确：

- 最多只有一个兵站。
- 玩家重生时间较长。
- 依靠轻型车辆进行运输和增援。
- 默认仍在唯一兵站重生，再依靠轻型车辆运输到前线。
- 以后某些具体编制可以把指定轻型车辆配置为移动重生点。

待确认：

- 若车辆可作为重生点，需要确认车辆静止、存活、乘员、敌军距离、交战状态、座位和部署区域等条件。

### 2.4 机械化步兵营

已明确：

- 最多只有一个兵站。
- 玩家重生时间较长。
- 依靠步战车进行运输和增援。
- 默认仍在唯一兵站重生，再依靠步战车运输到前线。
- 以后某些具体编制可以把指定步战车配置为移动重生点。

待确认：

- 若步战车可作为移动重生点，其启用和禁用条件待确认。
- 摩步营与机械化步兵营共享“按具体载具 allocation ID 开启移动重生”的底层框架；哪些载具可用由具体阵营编制配置，不按大类别硬编码实体。

### 2.5 特种编制

已明确：

- 特种编制是独立的大类别。
- 某些具体编制可以完全没有支援技能；是否有支援由具体编制配置决定。

待确认：

- 兵站数量、队包权限、重生方式、载具限制、支援技能和 CD 均尚未定义。

## 3. 本阶段已经落地的框架

- 具体编制已经记录五种稳定大类别，并由战术平板 UI 按“阵营 → 大类别 → 具体编制”三级展示。
- 兵站与队包已经具备数据策略：启用状态、最大数量、队长/指挥官权限、方块血量和三类 CD；尚未把旧部署信标及未来队包方块接到这些策略上。
- 服务端重生等待已经按具体编制读取；`-1` 才继承原有 15 秒全局值。
- 摩步营与机械化步兵营已经可以用具体载具 allocation ID 声明移动重生候选；移动重生的车辆状态条件和实际部署点接线仍待确认。
- 载具条目已经可记录损毁补充 CD；自动补充状态机尚未实现。
- 支援目录与支援请求已经执行具体编制的 `all`、`none` 或白名单过滤；本阶段没有注册任何具体支援技能。
- 阵营级投票、选票存档、显式锁定和同阵营原子应用共享结果已经落地；自动截止、胜负和平票规则仍不推断。
- 所有新增配置均有有界校验；旧 version 1 目录在内存中迁移到 version 2，可选 MOD 缺失时继续失败关闭。

## 4. 尚未接线的运行时职责

- 让既有兵站方块读取具体编制策略，执行阵营共享、数量、队长/指挥官权限、血量与 CD。
- 制作队包方块及小队级存档、伤害和重生点逻辑。
- 根据以后确认的条件，把已声明的轻型车辆或步战车接成移动重生点。
- 为载具 allocation 增加损毁检测、补充资格和服务端权威 CD 状态。
- 接入以后确认的投票自动截止、胜负、平票及晚加入者流程。

## 5. 本阶段明确不做

- 不填写坦克、步战车、轻型车辆的具体实体 ID。
- 不填写各类编制的最终载具数量。
- 不填写重生、兵站、队包或载具补充的最终秒数。
- 不实现具体支援技能。
- 不擅自创建学院军或凯撒军的正式具体编制表。
- 不改变 `WOK-本体护甲` 或任何 WOK 本体模块。

## 6. 尚待确认的投票规则

以下规则会决定投票状态机行为，当前不得猜测：

- 蓝、红两方是否各自独立开启和结算投票。
- 玩家在投票截止前能否修改自己的票。
- 截止条件采用固定倒计时、管理员/开局流程触发，还是全员投完自动截止。
- 最高票同票时的处理方式。
- 投票已经锁定后加入阵营的玩家是否直接继承结果，以及下一轮何时允许重新投票。

## 7. 已落地的中立投票框架

在上述比赛规则确认前，代码已经提供不替产品做决定的底层能力：

- 学院军与凯撒军分别拥有独立投票状态。
- 玩家先只选择阵营，服务端允许持久化“有阵营、无编制”的等待状态。
- 每轮投票保存候选、玩家 UUID 对应选票、实时票数、是否允许改票以及锁定结果。
- 开启投票时由管理员显式传入是否允许改票；锁定时由管理员或以后接入的开局流程显式传入胜出编制。
- 锁定成功后，当时同阵营的所有玩家统一获得一个编制；晚加入者处理尚未写死。
- 世界重启保留投票，编制目录热重载会调和失效候选，战局重置清空投票。
- 当前尚未启用自动倒计时、自动选最高票或自动同票裁决；这些必须等产品规则确认后接入。
