# WOK步战核心

Minecraft 1.20.1 / Forge 47.4.22 的独立步战大战场核心，modId 为 `wok_infantry`，当前版本为 `0.1.0`。战术地图可软联动 JourneyMap 6 或 Xaero's Minimap 24.2；两者都不是核心加载所需的硬依赖，专用服务端也不需安装地图 MOD。
阵营、小队、兵种名额、部署、配装发放和战术标记均由服务端裁决。

## 设计参考边界

本 MOD 参考《Squad》的“阵营—小队—受限兵种—部署—指挥地图”组织骨架，参考《Into the Radius 2》战术终端的实体拼板层级，并参考 WARDOGS 的大规模合成作战与快速战场信息节奏。参考仅限玩法结构、交互层级与一般性视觉语言：

- 不复制两者的代码、资源、图标、界面素材、商标或网络协议
- 不宣称与原作品兼容、获得授权或存在官方关系
- 界面、服务端状态机、Minecraft 交互和数据格式均为 WOK步战自己的实现
- 每方有一个管理员配置的主基地、最多 15 个实体部署信标和一个独立的实体载具部署箭头；地图上的集结标记仍只是战术信息，不是出生点

## 已实现

### 阵营与管理员配装导入导出

- 管理员配装终端右上角“导入 / 导出”可整体迁移全部阵营、编制、兵种、装备池、白名单、载具规则和完整物品 SNBT；不包含玩家个人选择或对局运行数据。
- 导入须先预览，确认后自动备份并整体替换两个配置文件；同名导出、无效配置、预览后文件变化会被拒绝，写入中断可恢复。
- 数据包位于服务端 `config/wok_infantry/catalogs/`，支持 `/loadoutadmin export|import|files` 与 `/battle admin formation export|import|files`。权限等级 2；客户端和服务端须使用同一核心构建（配装协议 11）。详见 [导入导出说明](docs/CATALOG_IMPORT_EXPORT.md)。

### 手部 / 腿部体力与 TaCZ 联动

- 服务端分别维护手部与腿部体力：实际疾跑和跳跃消耗腿部，主手持 TaCZ 枪械开镜消耗手部；消耗停止后延迟恢复
- 腿部耗尽会强制结束疾跑，恢复到安全阈值后才可再次持续疾跑
- 任一部位低于 35% 时，TaCZ 开镜开始出现平滑呼吸摆动；手部疲劳为主，腿部疲劳提供较轻的冲刺后气喘影响
- 左下角人物部位血量下方的迷你双体力 HUD 复用 WOK步战战术配色，并对窄屏自适应；数值由服务端同步并随玩家保存
- TaCZ 1.1.8+ 仍是可选依赖；未安装或接口不可用时只关闭手部开镜消耗和枪械摆动，腿部体力与核心加载不受影响。模型、默认数值及验收清单见 [体力系统](docs/STAMINA_SYSTEM.md)
- 权限等级 2 可用 `/battle admin stamina status|set|reset` 验收、读取手部/腿部精确值并调参

### 阵营与编制

- 玩家进入战局后先选择公开阵营（默认骨架为学院军或凯撒），再选择该阵营下的编制；普通玩家本轮确认后不能自行切换
- 已经加入阵营但编制投票尚未开启或锁定时，可按 `Esc` 暂时关闭强制选择页，以便管理员执行投票或直接分配指令；尚未选择阵营时仍不能绕过该页面
- 学院军现有首个正式编制“千禧年研讨会机动部队”：3 辆 M1296 龙骑兵、2 辆 M1128 MGS、2 辆悍马 M2 与 1 架机枪版小鸟；编制选择页显示千禧年徽标
- 凯撒现有首个正式编制“234机械化作战单元”：1 辆豹2A4、2 辆 CV90 与 2 辆装甲无武装 HMMWV；豹2A4、CV90 战损后 15 分钟补充，HMMWV 战损后 5 分钟补充
- 编制目录由服务端 `config/wok_infantry/formations.json` 驱动，分别约束人数、小队呼号与容量、兵种配额、TaCZ 配装条目白名单和卓越前线载具清单
- 配装在部署与补给时再次按当前编制校验；首批载具由管理员在所属战斗侧的实体载具部署箭头显式整批部署，战损后仍从该箭头按槽位执行不可再生、5 分钟或 10 分钟的持久化补充规则
- TaCZ、卓越前线、FCP 与龙之崛起均为可选依赖；没有配置相应内容时，`wok_infantry` 仍可独立安装。完整 schema、命令和失败关闭边界见 [阵营与编制框架](docs/FORMATION_FRAMEWORK.md)

### 40v40 小队与兵种

- 两个内部战斗侧，每方硬上限 40 人；公开阵营和编制容量可以进一步降低上限，玩家必须显式选择而非自动分配
- 每个编制可配置 Alpha–Echo 中的任意小队集合，每队最多 8 人；同阵营不同编制的同名小队互相隔离
- 创建、加入、退出、二次确认解散、踢出、移交队长，以及每阵营唯一指挥官；申请、卸任和向在线小队长移交指挥权均可在 `K` 键界面完成；创建、加入、退出与解散只能在非存活部署状态操作；被踢成员 60 秒内不能重新加入或重建原小队，但可以加入其他小队
- `K` 键综合 UI：小队、兵种、部署、配装和战术地图入口；窄屏会重排状态与提示，部署点列表按可见行分页，不会让协议允许的后续部署点变成不可点击项
- 常驻小队 HUD：最多 8 人，显示队长/指挥官、在线、部署存活状态、生命值与兵种
- 仅同小队客户端可见的近距离头顶识别，不使用全局发光状态
- 四个基础兵种：突击兵、支援兵、工程兵、侦察兵
- 默认每队兵种上限：突击 8、支援 2、工程 2、侦察 1；突击兵固定启用且上限为 8，其他兵种可由管理员设置启用状态和 1–8 个名额
- 兵种名额由服务端原子占用；玩家处于 `ACTIVE` 时不能切换小队或兵种，需先重新部署

### 部署、重新部署与补给

每名玩家由服务端维护 `WAITING → READY → ACTIVE` 三阶段生命周期：

1. `WAITING`：首次进入、死亡、主动重新部署、战局重置或存活期间队伍关系被权威修改后进入等待。玩家进入 WOK步战专用空白维度的阵营隔离单元，以冒险、隐形、无敌、无碰撞状态等待；不会接收战场维度的区块、实体或声音。倒计时固定为 15 秒，期间可选择小队、兵种、配装、战场部署点，并可通过部署页的“整理个人物资”安全管理自己的末影箱。
2. `READY`：15 秒结束后可以选择己方主基地并申请部署。服务端再次校验阵营、小队、部署点、维度、安全落脚点、兵种和六槽配装；任一条件不满足都不会发放装备。
3. `ACTIVE`：校验通过后传送至主基地附近的安全位置、切换为生存模式，并且当前生命只发放一次装备。死亡或二次确认“重新部署”会清理本批装备并重新进入 15 秒等待。被管理员移出、战局已满或失去重连席位的玩家会回收战局装备并转移到第二个独立空白大厅维度，而不是留在可配置的战场维度或双方等待维度。

战局参与者处于 `WAITING`、`READY` 或 `ACTIVE` 时都不能通过下界门、末地门或第三方传送器擅自换维度；只有部署系统自己的等待、出战和大厅迁移会获得服务端内部授权。

每方当前有一个持久化主基地。权限等级 2 的玩家管理员可在战场安全脚点继续执行 `/battle deployment setbase <blue|red>`；玩家管理员、服务端控制台和 RCON 也可直接执行 `/battle deployment setbase <blue|red> <维度> <x> <脚部y> <z> [yaw]`，无需把等待管理员传出隔离区。显式命令省略 `yaw` 时采用命令源朝向。等待区、大厅、世界边界外、附近没有实体地面，或落脚区含水、岩浆、火、细雪、岩浆块、营火等危险环境的坐标会在保存前被拒绝，不会生成永久不可部署的坏基地。主基地默认补给半径为 8 格。玩家在 `K` 键部署页选择己方主基地或部署信标，也可通过部署点 UUID 使用命令选择。

权限等级 2 的管理员还可创建实体部署信标。最稳定且支持控制台/RCON 的服务端用法是 `/battle deployment beacon place <blue|red> <维度> <方块x> <方块y> <方块z> [yaw]`：指定位置必须为空气或已有信标，指令会原子放置并绑定阵营。玩家管理员也可在已经部署到战场、处于 `ACTIVE` 状态时使用 `/give @s wok_infantry:deployment_beacon` 放置灰色未绑定信标，再用蓝色或红色染料右键绑定，空手右键查询归属；信标和染料应放在快捷栏第 7 格以后或副手，不得替换六个兵种配装槽。等待中的管理员仍在隔离维度，应使用显式指令而不是尝试从等待区放置。信标会以蓝/红方块状态显示，拆除后自动注销并清除玩家的旧选择。每方最多 15 个信标；信标只是前线出生点，不是补给点。保存的中心落脚格临时被玩家或方块占用时，部署仍会在信标附近重新搜索安全位置。

编制载具使用另一种独立实体方块 `wok_infantry:vehicle_deployment`，不会再从玩家主基地生成。部署信标、载具部署方块、小型/中型弹药箱、龙之崛起原生 `dragonrise_reforge:ammo_supply_station` 大型弹药补给站和小队队包集中在创造物品栏独立分页“WOK步战 · 特殊方块”中。大型站直接沿用合作方原生部署器、实体骨骼模型和渲染，WOK步战核心只接管 1500 点补给规则；未安装龙之崛起时该分页不显示大型站，车辆也不会发出无效替代物。旧 `wok_infantry:large_ammo_supply_station` 只为已有存档保留注册，不再展示或发放。该页便于查找，但实际放置与拆除仍执行各方块既有权限。管理员可用 `/battle deployment vehicle place <blue|red> <维度> <方块x> <方块y> <方块z> [yaw]` 原子放置并绑定，也可从独立分页或 `/give` 取得方块，放下后用蓝色/红色染料绑定。方块表面凸起的 `→` 箭头就是载具批次的前向，放置时采用玩家朝向；潜行空手右键顺时针旋转，普通空手右键查询阵营与方向。每个内部战斗侧只能有一个载具部署方块，拆除即注销。实体方块缺失、区块未加载、阵营颜色或箭头方向与存档不一致时，首批部署和冷却补充均失败关闭，不会退回主基地生成。

已部署玩家只有位于己方主基地同一维度且处于补给半径内时才能补给。每次部署或补给后都有 60 秒服务端冷却；补给会重新校验完整配装，并以新批次替换旧批次。

大型与中型弹药补给可由指定载具运输。服务端配置 `world/serverconfig/wok_infantry-server.toml` 的 `supplyTransport.vehicles` 使用 `实体ID=large|medium=箱数`；默认包含 FMTV（`superbwarfare:truck=large=3`）、Ural（`fcp:ural=large=3`）、无装甲无武装 HMMWV（`fcp:hmmwv_unarmored_unarmed=medium=2`）和装甲无武装 HMMWV（`fcp:hmmwv_armored_unarmed=medium=1`）。旧式 `实体ID=箱数` 继续按大型补给解析。每个新出现的匹配载具只在第一次建立运输数据时按配置装满，补给规格及剩余数量保存在载具实体 NBT 中，区块卸载和服务端重启不会回满；降低容量会截断超额库存，提高容量也不会给旧车免费补箱，改变补给规格不会把旧库存转换成另一种箱子。已部署玩家在通过该编制载具的阵营/编制授权后，可空手潜行右键车辆逐箱取出对应补给并放到地上。取出的箱子属于当前生命，可在背包与快捷栏之间移动，但不能丢弃、转交或带到下一条生命；死亡、重新部署或战局会话失效都会使它随本批装备一起回收。只要身上还有至少一个大型箱，服务端就强制结束疾跑，并按 `supplyTransport.carrySpeedMultiplier` 降低移动速度，默认保留 25%；中型箱暂不套用大型箱负重减速。背包无空间、车辆已空、权限不符或对应补给物品不可用时均不会扣除车载库存。所有正式车辆配置统一维护在[车辆运输补给容量清单](docs/SUPPLY_TRANSPORT_CAPACITY_LIST.md)。

`wok_infantry:medium_ammo_supply_crate` 是 500 点中型弹药箱，与 100 点小型箱使用同一套选枪补给事务；外观复用可选客户端模组 `doomsday_decoration` 的武器箱模型。`wok_infantry:rally_radio` 是小队队包，外观复用同一模组的无线电；服务端按 `capabilities.rally` 校验放置权限、每队上限和生命值，并只把存活队包提供给所属小队作为复活部署点。即使客户端伪造部署点 ID，服务端在选择与实际复活前也会按当前阵营、编制和小队重新匹配；Alpha 只能使用 Alpha 的队包，不能借用 Bravo 的队包。新生成的默认编制为每队 1 个、100 生命，小队长或指挥官可放置；旧 `formations.json` 保留原配置，需显式将目标编制的 `capabilities.rally.enabled` 设为 `true`。每次成功部署后，同阵营、同编制、同小队立即进入固定 8 分钟部署冷却；冷却持久化到世界存档，主动撤收、被摧毁或服务端重启均不会提前清除，其他小队不受影响。队包友伤关闭，近战、投射物和爆炸每次分别扣 10、25、100 点；右键查询生命，所属小队长/指挥官潜行右键可主动撤收。

### 配装与安全发放

- 六个必需槽位：主武器、副武器、近战武器、战术道具一、战术道具二、投掷物
- 玩家配装 UI：按 `L` 或执行 `/loadout`；管理员编辑 UI：按 `U`（可在按键设置中修改）或执行 `/loadoutadmin`，需要权限等级 2
- 职业由具体编制独立拥有：管理员可在“职业管理”中新建、重命名、调整每小队名额、删除职业，或用“↑ 上移 / ↓ 下移”调整显示顺序；例如可排列为“队长、步枪兵、其他职业”，不会改变其他编制
- 新建职业会生成只供当前编制使用的独立装备池；玩家进入该编制后，小队职业页和配装页只显示该编制拥有的职业，并使用编制保存的顺序。显示顺序不再决定人数限额或兜底身份：队长可以排第一并保持 1 人，系统会选择顺序中第一个能够覆盖每支小队全部席位的职业（通常为 8 人步枪兵）负责入队与异常调和
- 管理员终端顶部可依次选择阵营、编制、职业与槽位；列表中的“仅此 / 加入 / 移出 / 全部开放”直接维护该编制职业的严格配装白名单，不再需要手改 `formations.json`
- 管理员终端会在同一客户端会话内记住最后编辑的阵营、编制、职业与槽位，关闭后重新打开会回到原位置。顶部“复/贴”只深复制当前兵种的装备槽位、物品、SNBT 与白名单，可粘贴到同编制或其他编制的另一个兵种；粘贴前必须确认，复制后两边装备池互相独立，目标兵种名称、顺序、名额以及其他兵种、载具、能力和生成规则都不会被覆盖。已经使用目标兵种的玩家会保持原职业，只切换到新生成的私有装备池
- 每个枪械装备条目可在单件装备编辑页独立配置“该枪械携带/补给弹药上限”，范围 1–4096 发，默认 180 发。部署时服务端把该值写入实际发放的枪械；小型弹药箱和大型弹药站按玩家点选的那把枪执行，因此同一职业的步枪、手枪与发射器可以使用不同上限。没有部署标记的管理员测试枪才回退到服务端全局值；超过上限的已有弹药不会被强制删除，装备条目的初始物品数量仍由“数量”决定
- 每次服务端战局会话中，玩家第一次成功部署会按已装备枪械的逐枪上限免费取得物理备用弹药；使用相同弹种的多把枪共享库存，并取其中较高上限。首批发放完成后，死亡或主动重新部署只重发职业配装，不再补满备用弹药，避免以重新部署代替主基地、弹药箱与运输补给
- 每个兵种/槽位可新增、修改、删除全局候选装备，并配置物品注册名、数量和可选 SNBT；点“读取主手”会由服务端直接保存当前物品及 TaCZ 枪械配件数据，并把新条目加入当前所选编制的严格白名单
- 部署或补给前必须一次性成功解析全部六槽；缺项、禁用兵种、无效物品或损坏 SNBT 都会使整个发放失败，不会部分发放
- 六槽固定写入快捷栏第 1–6 格。部署前服务端会对一般物品栏、副手、个人 2×2 合成输入、光标物品、护甲和末影箱做零修改预检；普通物品可在容量允许时事务性转存到末影箱，护甲保留。ACTIVE 玩家死亡前，服务端会把普通护甲写入玩家 namespaced 持久化暂存区并清空原槽，重生或重连时只恢复到原来的空槽；已有物品绝不覆盖，无法明确验证的数据继续隔离保存
- `WAITING` 的个人栏只禁止合成槽；部署页可打开服务端识别的本人末影箱整理界面。只有来源扫描为普通的物品可移动，其他箱子、合成结果和战局装备仍在原版处理前拦截
- `ACTIVE` 期间配装及护甲槽由服务端锁定，个人栏和外部容器的点击、拾取、丢弃、个人合成、方块/流体放置及异常普通产物会被阻止或回收；快捷栏选择和正常使用装备不受影响。当前测试构建临时允许权限等级 2 管理员跳过每 tick 的活动配装来源校验，便于通过创造栏或 `/give` 保留测试物品；普通玩家仍执行完整校验，容器点击、拾取/丢弃及方块/流体限制也未关闭
- `/loadout apply` 仅对权限等级 2 开放，并作为补给入口使用；它仍然要求玩家处于 `ACTIVE`、站在己方主基地补给范围内并满足 60 秒冷却

每批部署装备都带有服务端写入的 `wok_infantry_kit` provenance，包含本次服务端会话、所有者和发放批次令牌。服务端据此执行以下防复制约束：

- 每生命只能成功部署发放一次；补给会生成新令牌并清除旧批次
- 登录、重生和玩家 tick 会清理异主、旧会话或旧批次装备
- 生命周期边界会扫描完整 ItemStack 序列化数据（含 Forge capabilities），并使用深度与节点预算拒绝不确定的嵌套容器
- 已发放装备不能被主动丢弃，死亡时不会成为普通掉落物
- 其他玩家不能拾取不属于其当前有效部署批次的装备
- 战局重置会轮换会话标识，使此前发放的装备全部失效

这些约束只作用于 WOK步战部署系统发放并带 provenance 的物品。普通物品不会因快捷栏占用而被覆盖；但若第三方能力背包绕过受控菜单、把战局装备嵌入自己的序列化数据，整个载体会被视为受污染数据并可能在生命周期清理时回收。正式服应先对能力背包、可存物护甲等 MOD 做组合验证。

普通护甲暂存以 Forge/原版死亡与 Clone 时序为受支持基线。若第三方墓碑、死亡背包或重生 MOD 另行复制/重放同一件护甲、篡改 WOK步战的私有 `PlayerPersisted` 暂存数据，或在同一最低事件优先级中更晚取消死亡，就存在无法自动判断物品所有权的兼容二义性。WOK步战不会覆盖已占用的护甲槽，会保留冲突或无法验证的暂存 NBT；当前版本尚无游戏内管理员恢复命令，因此这类 MOD 组合必须在正式服使用前单独验证。

### 战术地图

- `M` 键打开 WOK步战自己的战术地图，支持平移、缩放和图层切换
- 地图采用原创冷灰战术拼板：宽屏约 28% 的右侧命令板集中显示战区态势、2×2 图层、2×3 战术工具与选中目标卡；紧凑屏保留地图主体，并把六个标记工具收进独立底部抽屉
- 地图后端提供的地形会被统一成低饱和战术纸面，并叠加世界方位格号、动态比例尺、鼠标准星、内凹边框、角压条和铆钉；这些界面元素全部由 WOK步战代码绘制，不复制参考游戏素材
- 小队长/指挥官可发布步兵、坦克、步战车、进攻方向、防守和集结点标记
- 进攻方向使用玩家点击的精确起终点；客户端会先校验 4–4096 格长度，无效第二点不会清除起点；穿越视口的长箭头仍会绘制和选中，详情显示发布小队及剩余时间
- Alpha–Echo 使用稳定小队色；同队成员显示 1–8 编号，其他小队队长显示呼号，指挥官使用独立符号，悬停可查看小队、名字和兵种
- 等待部署时地图自动使用己方部署点所在战场维度并以基地为中心，因此死亡后的队长/指挥官仍可查看友军态势并发布合规标记；服务端只接受当前维度或己方部署维度
- 标记仅发送给同阵营玩家，默认 3 分钟失效，并有数量、频率、维度、坐标和世界边界校验
- 阵营过滤、发布权限、标记所有权与过期时间始终由 WOK步战服务端裁决
- 客户端提供通用 `TacticalMapAreaOverlayRegistry` 区域覆盖入口；可选附属只提交有限区域、名称、颜色、进度和锁定状态，核心统一裁切与绘制。安装 `WOK步战附属-占点` 后，A/B/C/D 等据点会自动显示在战术地图；未安装时地图行为不变

### 指挥支援框架

战术地图右侧命令板预留“支援模块”，宽屏固定显示在选中目标卡下方，紧凑界面通过“标记 / 支援”切换进入。`WOK步战核心` 本身不内置任何可调用技能，不绑定任何第三方 MOD、实体、武器或爆炸效果；仅安装核心时空目录是正常状态。安装独立的 `WOK步战附属-指挥官支援` 后，会注册“侦察卫星”、千禧年专属“F-15EX 杰达姆 1000磅空袭”和通用“F-16C GBU-12 宝石路 II 500磅精准空袭”；两种空袭缺少 Create Big Cannons 时只显示不可用，F-16C 还要求卓越前线火炮指示器，不影响侦察卫星。

支援扩展可在物理客户端通过 `TacticalSupportMapPresentationRegistry` 声明通用、情报或攻击性地图语义。攻击性点目标会按服务端定义的真实半径显示填充危险区、斜线和落点准星，方向型攻击显示完整波及走廊；注册只影响显示，不能修改服务端范围、冷却或执行逻辑。未声明的扩展按通用支援安全显示。

后续支援由服务端扩展通过注册 API 提交稳定 ID、显示信息、目标模式、冷却/来袭时间、覆盖边界和执行 provider。扩展负责自己的可选依赖与实体实现；核心只保存和传输经过校验的通用定义，不根据已安装 MOD 自动猜测或注册技能。同一个稳定 ID 不能重复注册，目录与 provider 不完整时按不可用状态失败关闭。

框架保留服务端权威边界：客户端只发送技能 ID、维度和 X/Z 目标意图，服务端重新校验当前战局、阵营指挥官身份、部署阶段、维度、有限坐标、世界边界、已加载区块、阵营冷却、执行中任务和请求幂等 ID。玩家不能提交 Y 坐标、冷却、范围或直接生成实体。普通队员只读取己方目录与整备状态，不能提交调用；敌方不会收到目标、冷却或任务信息。

已注册支援的冷却按阵营和稳定 ID 持久化，活跃任务只保留在当前服务端运行期。任务执行采用有界队列和每 tick 预算；扩展执行失败不会退化成核心自带的替代伤害。完整扩展边界见 [指挥支援框架](SUPPORT_SYSTEM.md)。

核心还向侦察类扩展提供受限临时情报接口：接触点只进入己方战术地图快照，以红点显示，不占小队长/指挥官手工标记额度，也不会写入世界存档。普通默认编制允许侦察卫星与 `wok_commander_support:f16c_gbu12_paveway_500lb`；`millennium_seminar_mobile` 额外允许 `wok_commander_support:millennium_f15ex_jdam_1000lb`。已有 `formations.json` 需要由管理员显式补入对应 ID；`support.mode=all` 会按管理员配置开放全部已注册支援。

## 数据文件

- 管理员配装配置：`config/wok_infantry/loadouts.json`
- 玩家配装选择：`<世界>/data/wok_infantry/player_loadouts.json`
- 战局、小队、指挥官、兵种占位和战术标记：`<世界>/data/wok_infantry_battle.dat`
- 蓝/红双方主基地、实体部署信标和载具部署箭头：`<世界>/data/wok_infantry_deployment.dat`
- 已注册支援的阵营冷却：`<世界>/data/wok_infantry_support.dat`（默认空目录不会写入技能记录）

第一次启动服务器时会自动生成默认配装配置。主基地会随世界保存；玩家当前的 `WAITING` / `READY` / `ACTIVE`、倒计时、补给冷却和发放令牌只在本次服务端运行期间存在。服务端重启后玩家会重新进入部署等待，旧会话装备会失效。

首次生成的默认配装只是管理员编辑骨架：主、副武器使用 `minecraft:air` 占位，另外四个必需槽位为空。管理员必须先通过 `/loadoutadmin` 为参与首测的兵种补齐六槽，否则服务端会按设计拒绝部署，不会发放半套装备。

单人功能测试可在游戏完全退出后，先备份并用 `dev/vanilla_test_loadouts.json` 替换实例的 `config/wok_infantry/loadouts.json`。该文件只使用原版物品，用于走通部署事务，不代表正式 WOK步战配装。随后用显式基地指令分别把双方基地设到战场安全脚点，例如 `/battle deployment setbase blue minecraft:overworld -64 -60 0 90` 和 `/battle deployment setbase red minecraft:overworld 64 -60 0 -90`；玩家加入小队、等待 15 秒、在部署页重新选择己方基地后即可部署。正式地图仍应由管理员在各自实际出生区设置双方基地并配置正式武器。

兵种启用状态与小队名额应在开局前确定。管理员在比赛运行中删除小队、降低小队容量或兵种名额后重载编制目录时，服务端会确定性调和旧 roster；受影响的存活玩家会撤回当前批次装备并回到部署等待，避免继续使用已经不属于其编制的配装。

## 战术地图地形后端

WOK步战核心现在按软依赖接入两种客户端地形后端：JourneyMap `[1.20.1-6.0.2,1.20.1-7.0.0)`，以及 Xaero's Minimap / Fair-play `[24.2.0,25.0.0)`。两者可以同时安装；JourneyMap 存在时固定优先使用其持久地形瓦片，Xaero 继续保留自身地图数据与 UI 兼容逻辑但不抢占 WOK 地形后端。只安装 Xaero 时使用 Xaero 的本地缓存地形；两者都未安装时仍可加载核心并使用坐标网格。步战专用测试整合包当前同时启用 JourneyMap `6.0.2`、Xaero Fair-play `24.2.0` 与 Xaero World Map `1.39.9`。

测试整合包中的 HUD Compass `0.5.9` 当前保持禁用：它把 JourneyMap 可选依赖声明为 `[5.9.8,)`，Forge 无法把 JourneyMap 6 的 `1.20.1-6.0.2` 版本字符串判定为满足该范围，启用后会在预加载阶段中止客户端。WOK 战术地图自带罗盘，因此禁用它不影响战术地图方向信息。

Xaero 联动通过反射读取其已经缓存的 4×4 地形瓦片，并用客户端当前已加载区块补齐近处空白。它不链接、shade 或重新发布 Xaero class；Xaero API/内部结构变化时会安全退回坐标网格而不是阻止游戏加载。WOK 战术地图打开期间会持续关闭 Xaero 原生小地图显示，但不会改写或保存玩家的 Xaero 配置文件。Xaero 没有为本集成提供等同 JourneyMap 区域导出的公开接口，因此未探索和未加载区域不会被伪造成完整地形。

JourneyMap 6 仍是受支持的可选后端，不是玩家可直接使用的第二套地图 UI。安装兼容版本后，JourneyMap API 2.0 插件为 WOK 战术地图异步提供真实地形瓦片；未安装、使用 JourneyMap 5.x 或未来未验收的 7.x 时，不再阻止 WOK步战核心加载。

玩家只使用 `M` 键打开 WOK步战战术地图。JourneyMap 自带小地图由公开 API 持续禁用，任何打开 JourneyMap 全屏地图的尝试都会被重定向到 WOK 战术地图。JourneyMap 仍在后台记录已加载/已探索的地形：

- 平移与缩放请求会防抖；过期回调会被丢弃
- 可视范围拆成区域边界对齐的 32×32 区块瓦片并按中心优先加载；同屏最多请求 96 块，每批最多提交 4 块且最多 4 块并发，并限制重试、LRU 块数和总像素；超过预算的战略缩放使用坐标网格，避免创建数百个动态纹理
- JourneyMap 请求超过 10 秒后，该界面不会在旧回调完成前重复提交同一瓦片；仍匹配当前界面的晚到结果可继续使用，过期结果会安全关闭，正常失败回调则按 5 秒退避重试
- 客户端全局最多保留 8 个尚未回调的地图宿主任务；重复打开地图或换维后对相同瓦片只沿用一次宿主请求，并把结果交给最新界面，旧界面通过弱引用释放，避免反复开关地图累积回调与 Screen 引用
- 替换瓦片或关闭界面时会释放动态纹理
- 缩放清晰度跨档时会保留同区域的旧地形，新瓦片到达后再无缝替换，不整屏闪回网格
- 尚未探索的 JourneyMap 区域、单块缺失、请求失败或视口过大时保留坐标网格，并显示初始化/加载/失败/需要放大的状态

JourneyMap API 编译依赖固定使用 `compileOnly 'info.journeymap:journeymap-api-forge:1.20.1-2.0.0'`，不会 shade、内嵌或重新发布 JourneyMap/API。WOK步战产物不得包含任何 `journeymap/**` 或 `xaero/**` 第三方 class；地图后端均作为独立客户端 MOD 发放，服务端无需安装。UI 验收仅把原版第三方 JAR 加入测试运行时，第三方文件不会进入 WOK 生产 JAR。

当前 JourneyMap `6.0.2` 隔离客户端验收已通过：公开 API 对 `minecraft:overworld@0,0` 返回 `512×512`、含 38,400 个非零像素的 Topo 图块；320×240 视口在截图前等待 `4/4` 瓦片，960×720 视口等待 `16/16` 瓦片，不再只加载一块就判定通过。同一轮还实际验证 JourneyMap 小地图禁用、JourneyMap 全屏图重定向、选点部署、六槽发装、K/M 网络开屏、队长/指挥官、四类标记、紧凑/宽屏支援空目录、编制共享投票状态机与 11 张截图。当前结果在 `run/ui-test/ui-test-results/wok_ui_acceptance.txt`。

JourneyMap `6.0.2` 的公开区域合并器不能安全裁切任意未对齐的小图块；WOK步战正式实现固定使用其支持的区域边界对齐 32×32 区块请求。不得在未重跑真实 API 回调与纹理上传验收的情况下缩小或取消这一对齐。全新 JourneyMap 数据目录只会逐步显示客户端已加载/已探索区域；未映射区域保留网格。如果正式预制战场要求所有玩家开局就看到整张地形，需要在发包时预生成并分发同一份 JourneyMap 地图缓存。

集成依据：[JourneyMap Integration 文档](https://teamjm.github.io/journeymap-docs/6.0.x/tools/integration/)、[JourneyMap API 2.0 使用说明](https://github.com/TeamJM/journeymap-api/blob/1.20.1_2.0.0/docs/howto.md)。

## TaCZ

本 MOD 不强制依赖 TaCZ。管理员可以把 TaCZ 枪械条目写入 `loadouts.json`，再由 `formations.json` 按兵种和槽位引用其稳定条目 ID。服务端在部署或补给时会重新检查编制白名单，并通过 TaCZ 公共 API 校验 `tacz:modern_kinetic_gun` 的 `GunId` 和构造结果；无效条目失败关闭，不会退回成另一把枪。同一配装机制也可以配置其他武器 MOD 的物品。TaCZ 的这项可选用途属于配装框架，与当前默认空目录的指挥支援框架相互独立。

权限等级 2 的管理员可把一把 TaCZ 枪拿在主手并按默认 `O` 打开战术平板式单枪编辑器；按键可在 Minecraft 控制设置的 WOK步战分类中修改，`/battle admin weapon edit` 继续作为指令入口。开镜速度、垂直后坐力、水平后坐力和散布均使用 25%—1500% 倍率（最高 15 倍），并在 TaCZ 完成枪械、瞄具与握把等配件属性计算后叠加。值与唯一编辑标识只写入当前 `ItemStack` 的 WOK步战命名空间 NBT；打开与应用数据包都会在服务端重新核对管理员权限，应用时还会核对主手枪械标识，因此不会改写枪包 JSON、注册表或其他同型号武器。单项恢复与全部恢复会删除相应倍率并立即重建 TaCZ 属性缓存。

玩家配装候选卡、选中装备详情和管理员装备列表会优先读取 TaCZ 右下角枪械 HUD 使用的原生 `39×13` 剪影纹理，并放入深色器材窗中等比显示。剪影通过可选反射从完整枪械 `ItemStack` 解析，因此会服从枪械包与枪械显示/皮肤数据；TaCZ 未安装、枪械配置无效或 HUD 纹理不可用时，界面安全退回普通物品图标，不影响核心独立启动。该预览不会复制或打包 TaCZ 的纹理。

## 当前验证边界

代码中的人数上限、名额与网络过滤按 40v40 设计，并提供 Forge GameTest：使用真实 `MinecraftServer`、`ServerLevel` 与 `ServerPlayer` 对象验证阵营/编制容量、同名小队的跨编制隔离、8 人小队边界、兵种名额、四类必需战术标记、敌方过滤、纯小队长/纯指挥官/普通成员的发布与删除权限矩阵，以及离队/踢出/解散后的队长、指挥官和兵种占位清理。客户端单元测试另行锁定同队头顶识别的单快照门禁、部署点分页几何、中英文键值/格式参数一致性：本人、其他友军小队、旧观察者、离线/非存活、隐形与 96 格外目标均不显示，协议允许的 16 个部署点在 320×240 最小视口仍可逐页到达。

`src/uiTest` 还提供一次真实 Forge 客户端验收：从隔离存档登录，通过共享投票夹具完成“开启投票→选阵营→投票→锁定共享结果”，再验证部署页。它通过实际 `K` / `M` 键绑定及 C2S/S2C 回路开屏，真实鼠标点击兵种页，创建 Alpha 小队、申请指挥官、在稳定安全平台设置本轮专用基地，再通过生产客户端动作发送选择和部署包。验收必须等到服务端确认 `ACTIVE`、客户端进入生存模式并收到六个带 provenance 的配装槽；随后临时授予管理员权限，把部署信标和阵营染料放入非配装槽并跨越多个服务端校验周期，最后逐个等待服务器确认步兵/坦克/步战车/进攻方向标记。部署点选择与部署在当前验收器中是直接调用同一客户端动作桥，不是鼠标点击按钮。纯布局单测固定覆盖 320×240、960×720 与 2560×1351，验证地图、右侧命令板、工具抽屉和状态栏互不重叠；真实客户端验收则分别检查 320×240 与 960×720 逻辑界面，并输出部署、小队、兵种、指挥官、地图和编制投票共 11 张截图。结果写入 `run/ui-test/ui-test-results/wok_ui_acceptance.txt`，截图写入 `run/ui-test/screenshots/wok_ui_*.png`；该 source set 不进入生产 JAR。

单元测试另有可重复的满载心跳容量工作负载：以蓝红双方各 40 人、五个满员 8 人小队和协议允许的完整战术标记构造 80 份观察者专属快照，连续运行 600 轮，共完成 48,000 次 `BattleSnapshot` DTO 到 `FriendlyByteBuf` 的编码。首尾轮会完整解码并再次检查敌方 UUID 不可见；本次基准单包为 13,308–13,416 字节，每轮 80 包合计 1,068,936 字节原始编码数据。该数值不含 Forge `SimpleChannel`、压缩、socket/TCP、服务器快照构建或真实客户端渲染，不得当作 80 个真实连接的性能结论。

`src/networkTest` 另提供三进程 Forge 回环验收：一个集成服宿主仅监听 `127.0.0.1`，两个外部客户端通过真实 TCP 分阶段登录并保持同时在线。验收强制核对 `3` 名在线玩家、`1` 条内存连接和 `2` 条非内存 TCP 连接；访客 A 通过 C2S 选择凯撒 `default` 编制、创建红方 Alpha 小队、选择支援兵并发布步兵标记，访客 B 选择学院军 `default` 编制、创建蓝方 Bravo 小队、选择支援兵并发布步战车标记，随后分别通过观察者专属 S2C 快照验证业务结果与敌方 UUID 隔离。宿主会再次从服务端权威状态核对两支小队、编制、兵种、标记以及协议 `8` 的支援服务空态。本次通过证据的 runId 为 `20260827T131620160Z-88a1c092a27b`：三方均报告 `supportOptions=0`、`supportActiveMissions=0`，结果写在 `run/network-test/results/`。验收代码不会进入生产 JAR，离线认证仅在该回环宿主内关闭，也不会接受或修改 EULA。

上述三进程验收证明了实际 Forge 登录以及两条 TCP 上的 C2S/S2C 主流程，但不是 80 名真实客户端的并发或吞吐压力测试；GameTest 玩家也只是隔离构造的服务端对象。因此现有验证仍不能替代 80 名真实网络客户端同时在线、批量 Forge 握手、登录/断线重连、传输背压或 ACTIVE 部署门禁测试。正式专用服仍需由服主自行同意 EULA 后完成首次世界加载；正式发布前仍需在 WOK步战附属专用测试环境完成多人阶梯压测、重连、死亡/重生、补给和防复制组合测试。

## 构建

需要 JDK 17：

```powershell
.\gradlew.bat build
```

开发用 Forge GameTest 目标可直接运行服务器对象验收；它不会修改 `run/eula.txt`，也不替代常规专用服务器所需的用户 EULA 确认：

```powershell
.\gradlew.bat runGameTestServer --no-daemon --console=plain
```

开发用真实客户端 UI 验收会重建自己的隔离存档并自动退出。JourneyMap 后端验收需要 `run/compat-cache/journeymap-forge-1.20.1-6.0.2.jar`，也可用 `-PuiJourneyMapJar=<路径>` 显式指定；无地图后端时可只跑坐标网格和通用 UI 路径。它不会接受 EULA，且验收器不会进入生产 JAR：

```powershell
.\gradlew.bat runUiTestClient --no-daemon --console=plain
```

开发用三进程回环联机验收会启动一个集成服宿主和两个隐藏的外部 Forge 客户端，仅使用 `127.0.0.1:25566`；需要地形后端断言时可加载 JourneyMap 6 测试夹具。脚本会分阶段启动访客、严格检查三方结果并按捕获到的 PID 树清理进程；它不会接受 EULA，且 `networkTest` source set 不进入生产 JAR：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\run_network_test.ps1
```

显式指定 JourneyMap 6 后端的 UI 验收命令如下；ForgeGradle 只会把该 JAR 加入 UI/网络测试运行时，并为 userdev 映射其 Mixin refmap：

```powershell
.\gradlew.bat runUiTestClient "-PuiJourneyMapJar=run/compat-cache/journeymap-forge-1.20.1-6.0.2.jar" -PuiExpectedTerrainProvider=journeymap -PuiExpectedJourneyMapLoaded=true --no-daemon --console=plain
```

产物位于 `build/libs/wok_infantry-0.1.0.jar`。
